# Auto Framing 开发计划

日期：2026-09-06。状态：首版代码与本地验证已完成；iPhone 真机与真实显示器效果待验证。

代码基线：本地 `main`，`9e5f6e5`，App 版本 `0.7.0 (13)`，iOS 18 / Swift 6。
该基线是实现前的检查点。下列章节包含真机反馈后的策略修订；实际完成情况与验证限制记录在文末。

## 目标与首版范围

在 Send Photo 和 Share Sheet 的 Fill 预览中提供「自动构图」。照片和目标准备好后自动应用一次，用户也可点击重做，
手机本地检测人脸与主体，按当前预览屏幕比例生成构图建议，并继续允许手动拖动和缩放。
最终复用已有 `ImageFraming`、按比例发送分组及 Share 队列。

- 按钮只处理当前预览比例；同一比例的设备共享结果，其他比例保持自己的构图。
- 自动放大上限为 2×，同时遵守服务器上限；根据主体群和人脸留边的范围计算放大程度。
- 分析使用 Apple Vision，不引入 Apple Intelligence、远程 AI 服务或额外照片库权限。
- 分析本身在本地完成；用户发送时仍沿用向 Tesserae 服务器上传图片的流程。
- 继续以服务器声明的 `image_framing` 和缩放上限控制兼容性。
- Gallery 已有的「发送此照片」进入 SendView 后复用此功能；Gallery 上传和 Offline Album 不增加自动裁剪。
- 首版不包含人物全身检测、OCR 文字保护、抠图、自动切换 Fit/Blur、批量处理或 Shortcuts 扩展。
- 无需新增服务端 API、协议字段、队列 schema 或固件功能。

## 交互规则

| 场景 | 行为 |
| --- | --- |
| 图片可用，已选择目标，Fill，服务器支持 framing | 当前照片的每个未编辑比例首次就绪时自动构图一次；按钮允许主动重做 |
| 未选目标、图片未准备好、其他 Fit 模式或服务器不支持 | 不提供可执行的自动构图入口；保持现有布局和预览目标行 |
| 点击按钮 | 记录当前图片、比例、编辑版本，启动或复用分析；按钮内显示进度 |
| 分析期间重复点击 | 不启动第二个分析任务 |
| 建议有效 | 更新当前比例的 framing，轻量动画；遵守 Reduce Motion |
| 可靠人脸无法同时放入裁剪框 | 保留当前构图，提示「无法完整保留所有人脸，可尝试 Fit 或 Blur」 |
| 普通主体太大或过于分散 | 允许局部裁剪，选择保留主体面积最多的位置；不因此拒绝构图 |
| 无可靠主体或无需改变 | 保留当前构图，轻量提示；不弹出阻断式错误 |
| 分析失败 | 保留当前构图，提示可重试；允许正常发送 |
| 手动拖动/缩放开始 | 立即使本次待应用建议失效；不等手势结束才处理 |
| 重置 | 当前比例回到 centeredFill，同时使待应用建议失效；不会再次默认应用 |
| 切换预览比例或移除目标 | 不向已经离开的比例悄悄应用结果；已完成的图片分析可继续缓存 |
| Fill 切到其他模式再切回 | 保留已确定的各比例构图，旧任务不能自动恢复应用 |
| 点击发送 | 取消待应用建议，固定当下图片、Fit、构图和目标快照；按该快照发送 |
| Share 首次请求已经入队 | 构图、Fit 和目标不再编辑；Retry 继续使用已保存请求。取消后仍遵守现有队列保留语义 |
| 换图、换服务器、退出页面 | 使待应用结果失效；换图时释放上一张图片的分析缓存 |

保留拖动提示、缩放倍率与重置。普通字号使用单行控制条，短状态词替换手势提示，不增加提示行；
文字可缩小或截断，不挤压倍率和重置。辅助字号的操作区放到图片下方。
不要让控制条溢出或侵入预览目标选择行。按钮提供 VoiceOver 名称、状态和操作范围说明。
App 与 Share 的中文翻译分别进入各自的 `zh-Hans.lproj/Localizable.strings`。

## 模块与数据流

建议新增以下文件，名字可以随实现作局部调整，职责保持一致：

| 新增文件 | 职责 |
| --- | --- |
| `Packages/TesseraeKit/Sources/TesseraeKit/AutoFramingSolver.swift` | 值类型的区域模型、算法策略、纯几何求解与明确的结果原因 |
| `SharedUI/PhotoSubjectAnalyzer.swift` | 可注入的分析协议与 Vision 实现，生成标准化人脸和主体区域 |
| `SharedUI/PhotoFramingSession.swift` | 主线程 UI 状态、图片身份、各比例构图、编辑版本、任务与缓存 |

数据流：准备好的图片 → 缩略图分析 → 标准化检测区域 → 按比例求解 → 更新现有预览 → 固定发送请求。

分析结果使用可跨并发边界传递的值类型，至少包含图片身份、源尺寸、人脸区域和主体区域。
求解结果区分 `suggested`、`unchanged`、`noReliableSubject`、`cannotPreserveSubjects` 和无效输入；
框架执行错误由分析层处理，不把错误当成一份有效的居中建议。
UI 文案放在展示层；求解器不持有照片、SwiftUI 状态或服务器连接。

### 图片准备与 Vision

1. PhotosPicker 输入沿用 `UploadImagePreparer`。加载请求的身份在 `loadTransferable` 之前生成，
   每次异步返回都检查，避免快速换图时旧图片覆盖新图片。
2. `SendImageDraft` 初始化来自 Gallery，当前可直接透传图片数据。让该入口也经过一致的方向准备，
   然后用同一份 prepared data 更新预览与发送源；已正向且无需缩放的图片沿用准备器的透传路径。
3. Share 现有加载流程已调用准备器，直接把该输出交给共享会话；不额外复制一份完整图片状态。
4. 首次自动应用或点击 Auto Frame 时创建分析缩略图，长边初始上限 1536 像素且不放大小图。
   保持整幅图比例，不对缩略图预先裁剪。此值是待真机评估的工程起点。
5. 使用 `DetectFaceRectanglesRequest` 与 `GenerateObjectnessBasedSaliencyImageRequest`。
   同一会话最多分析一张图片；可共用 ImageRequestHandler，不并发排队处理相册。
   缩略图解码及分析工作不占用主线程，不强行指定 GPU/CPU。
6. Vision 区域从左下原点转换为左上原点：`x = minX`、`y = 1 - maxY`，宽高不变。
   丢弃非有限数值、空矩形和无效范围，合理裁到单位矩形。保持所有有效主体区域，不依赖返回顺序。
7. 成功结果只缓存在当前照片的会话内，包含无主体结果；切换目标比例不重新执行 Vision。
   用户退出或换图后释放结果和分析缓冲区，不持久化人脸信息、热力图或照片副本。

### 首版求解策略

以完整人脸保护为主要约束，以主体保留程度为次要目标。该策略不声称能识别用户真正想保留的人物。

1. 先由 `resolvedCrop()` 求出普通 Fill 的裁剪宽高。合并主体与留边人脸得到构图范围，
   用其相对于普通 Fill 的最长边比例计算 zoom，使构图范围占裁剪框约 85%；zoom 限于 1…min(2, 服务器上限)。
   大主体保持 1×，小主体可以放大；最终裁剪宽高 `cw`、`ch` 为普通 Fill 宽高除以 zoom。
2. 人脸置信度筛选的初始阈值设为 0.8；初始留边为脸框自身宽高的 15%。
   这些值集中在可测试的 policy 中，属于待真实照片校准的参数，不当作质量保证。
   人脸置信度不与显著性区域数值直接混合比较。
3. 对可靠人脸求包围矩形，检查能否整体容纳。先尝试留边区域；留边不可行但原始脸框可行时，
   降低留边要求。连原始脸框都放不下时返回 `cannotPreserveSubjects`，不擅自挑选某一个人。
4. 对需要完整保留的矩形 `B`，合法裁剪原点满足：
   `x ∈ [max(0, B.maxX - cw), min(1 - cw, B.minX)]`，y 方向同理。
   区间为空表示无法完整保留人脸。没有人脸时，在整个合法 Fill 平移范围内选择主体可见面积最大的位置，
   不要求完整容纳主体框；重叠面积仍按并集计算。整幅图被标为主体且各位置得分相同时保留居中偏好。
5. 在合法范围内，以主体边界、主体中心和居中位置生成有限候选，去重后比较主体可见面积。
   重叠主体框的面积按并集处理，避免重复计分；评分相同时，1× 偏好原图居中，放大时偏好构图范围中心，排序保持稳定。
   有人脸时主体作为次要目标，不能为提高主体面积而裁掉受保护人脸。
6. 以胜出裁剪矩形的中心生成 `focusX` / `focusY`，再调用现有 `resolvedCrop()` 验证最终范围与人脸约束。
   所有最终 focus 必须有限且处于 0…1，zoom 处于 1…min(2, 服务器上限)。
7. 无可靠区域时保留当前 framing。如果建议对应的实际裁剪与当前裁剪相同，在浮点容差内返回 unchanged。
   用户主动点击可重新计算位置和 zoom；没有有效建议时不重置用户的手动结果。

4:3 横图放入 3:4 竖屏时，zoom 1 的可见宽度仅为源图的 0.5625。
多人跨越更宽区域时无法靠移动解决；不得生成 zoom < 1 或自动切换 Fit 来隐藏该限制。

### 会话与并发规则

- 使用图片身份 + 请求代次 + 当前预览比例 + 该比例编辑版本校验应用资格。
- 每张图片按比例记录已尝试自动应用或发生手动操作的状态，模式往返、重置和重进不会重新覆盖；换图清空记录。
- 分离「分析缓存仍可用」与「允许自动应用结果」：离开当前比例后可以缓存分析，但不能修改已离开的构图。
- 手势开始回调至关重要：现有预览在 `.onEnded` 才写入 framing Binding，只观察 Binding 会漏掉拖动中的覆盖竞态。
- 重置、模式变化、服务器上下文变化、发送和页面退出都撤销应用资格。
- 取消是尽力而为；即使 Vision 没有立即停止，也必须丢弃过期回调，不能据此写 UI。
- Send 使用固定的图片/Fit/分组快照构造已有幂等签名；编辑后的下一次主动发送生成新签名。
- Share Retry 复用队列里的 framing 和幂等键，不能重新分析，也不能展示已修改但不会实际发送的构图。

## 实施顺序与完成条件

按单代理顺序实施，共享核心先于两个入口接入，便于保持同一套行为。

| 阶段 | 工作 | 完成条件 |
| --- | --- | --- |
| 1. 纯计算 | 区域模型、策略、坐标辅助计算、求解器与单元测试 | 合照可行/不可行、边缘脸、横竖比例、无主体、非法输入均得到可解释结果 |
| 2. 分析与会话 | Vision 适配器、缩略图、缓存、取消与编辑版本；注入可控制完成时序的假分析器 | 快速换图、手势开始、切比例、退出、失败/重试不会应用过期结果 |
| 3. Send 端 | 接入 Photos 与 initialImage，增加共享按钮及手势回调，固定发送快照 | 演示流程可应用建议、继续调整、切目标、发送；未使用自动构图的路径保持原有行为 |
| 4. Share 端 | 复用分析和会话，处理图片可见性及入队后的编辑锁定 | 与 Send 行为一致，首次发送及离线重试的实际参数等于确认的预览 |
| 5. 集成验收 | 工程生成、本地化、无障碍、文档与 Changelog，构建及真实图片对照 | 分别记录纯计算、App 测试、两个 target 构建、真机及服务器渲染证据 |

预计新增测试文件：`AutoFramingSolverTests.swift`（TesseraeKit），
`PhotoFramingSessionTests.swift` 与必要的分析适配测试（App/Tests）。
复用 `PanelPreviewGeometryTests`、`UploadImagePreparationTests`、`ShareQueueStoreTests` 和现有 Send UI 流程。
Share 发送冻结规则如需新增辅助对象，做成共享可注入逻辑，以便在已有 App 测试 target 中验证，

## 验证清单

这是完整验收范围；下方执行记录只勾选已取得证据的部分，真机及真实照片质量不以模拟器测试代替。

- [ ] 纯几何：单脸偏边、两脸可容纳/不可容纳、留边降级、主体去重、无主体、同源目标比例、极宽/极高图片、无效输入。
- [ ] 方向：EXIF 旋转及镜像输入；缩略图和上传图的标准化坐标一致，横纵坐标不翻转。
- [ ] 会话：A 图慢任务晚于 B 图完成；拖动刚开始；重置；切比例；移除目标；退出/重进；发送中返回分析结果。
- [ ] 缓存：同图切比例只分析一次；无主体结果可缓存；失败可重新请求；换图后释放旧缓存。
- [ ] 兼容：旧服务器、无目标、其他 Fit 模式、图片 URL/网页来源不显示错误的可用入口。
- [ ] 发图：同/异比例分组正确；预览确定的 framing 进入真实客户端请求；提交时快照稳定。
- [ ] Share：离线入队再重试不重新分析；framing 和幂等键保持；提交及 Retry 状态不能产生预览与请求差异。
- [ ] UI：窄屏、中文、最大辅助字号、VoiceOver、Reduce Motion；复用现有画布命中区域，黑色边框拖动不修改构图。
- [ ] 自动化 UI 使用固定区域的假分析器，验证交互和发送；不把特定系统版本的 Vision 检测框作为像素级断言。
- [ ] 真实照片使用本地获准样本或许可明确的公开样本；私人照片、服务器地址和家庭数据不提交仓库。
- [ ] 真机样本覆盖单人、多人、宠物、风景、海报、低光、边缘脸和截图；记录建议改善、无变化与退化案例。
- [ ] 性能记录首次及重复分析耗时、峰值内存、设备/iOS、源图尺寸；至少覆盖可获得的较旧兼容 iPhone及 Share 环境。未覆盖设备明确记录。
- [ ] 对照实际服务器渲染预览和至少一台显示器；几何位置应一致，颜色量化/抖动不以手机照片预览作为像素等价标准。
